❯ is supabaseAdmn the idiomatic way to do crud requests with supabase?

Ran 1 shell command (ctrl+o to expand)

⏺ It depends on where the code runs and who enforces permissions.

What Supabase usually recommends is that the database enforces access, through
row-level security (RLS) policies. Requests come from a client with the
publishable key plus the logged-in user's access token. Postgres then knows
who the user is (auth.uid()), and the policies decide which rows that user can
read or change. That's the standard setup when a frontend talks to Supabase
directly. A backend can do the same thing by creating a client for each
request that sends the user's token in the Authorization header.

The secret key (supabaseAdmin) is meant for trusted server code. It ignores
RLS completely. Using it for CRUD is common and fine when you have your own
backend, like this Express app, and your code is the security boundary. Every
permission check then has to live in the service layer, like the "only the
creator can edit" check in pinService. A missed check means anyone can read or
change any row.

What this repo does right now:

- Your migration turns on RLS for all five tables but defines no policies.
  That means anything not using the secret key is denied everything.
- pinRepository uses supabaseAdmin, so it works, and permissions depend
  entirely on the service code.
- collectionRepository uses supabasePublic, which is the publishable key with
  no user token, so it runs as anonymous. With RLS on and no policies, its
  selects will always come back empty and its inserts, updates and deletes
  will fail. It isn't the RLS approach either, since that also needs the
  user's token on each request.

So the two repositories don't match, and only the admin one works today. There
are two consistent options:

1. Admin client everywhere, permissions checked in the services. This is
   closest to what the pin code already does, and the simplest fit for an
   Express backend.
2. A per-request client using the user's token, plus RLS policies written in
   SQL. The database enforces permissions, even if a service check is missed.
   It means writing policies and passing the token down to the repositories.

This is the open question Sunny's comment in pinRepository.ts asks, and it's
an architecture decision your team should make. I can lay out the trade-offs
in more detail or implement whichever option you pick.

❯ what are the trade-offs here?

⏺ Option 1: Admin client, permissions checked in the services

Pros

- Simple. One shared client and no SQL policies to write. Permission logic is
  plain TypeScript, which is easy to read and debug.
- Close to what already exists. pinRepository and the creator checks in
  pinService already work this way. Moving collectionRepository to
  supabaseAdmin is a small change.
- Complex rules are easy to write. "A collaborator with can_add_pins can add
  to a collection" or "anyone can view public collections" are simple
  conditionals in code. As RLS policies, the collection rules would join
  collection_members and collections (more on that under Option 2).
- Easy to test. Services can be unit tested with a mocked repository.
  Integration tests don't need real user tokens for every query.

Cons

- Every check has to be remembered. A forgotten check (say, on a new "list
  collections" endpoint) leaks or exposes data, and nothing else catches it.
- Each check costs extra queries. For example, updatePin first loads the pin
  to compare creator_id, which is two database calls.
- The secret key's reach is large. Any bug that lets a request bypass the
  service code can touch any row.
- The backend is the only safe way in. If the frontend ever queried Supabase
  directly, the "deny everything" RLS setting would block it. You'd need
  policies at that point anyway.

Option 2: User's token per request, plus RLS policies

Pros

- The database enforces permissions. Even a buggy or forgotten service check
  can't expose rows the policies deny. This is the standard Supabase approach.
- Rules live in one place. If the frontend or another service ever talks to
  Supabase directly, the same rules apply.
- Fewer permission queries. update pins where id = X simply affects 0 rows if
  the user isn't the creator. No separate fetch is needed first, though you
  lose the clear distinction between a 404 and a 403.

Cons

- More setup. You'd write policies in SQL for all five tables and manage them
  through migrations and db:sync.
- Plumbing. Each request needs its own client built from the user's token, and
  that client has to be passed from controller to service to repository.
  Today the repositories import one shared client.
- Policies that check other tables are tricky. Collection rules depend on
  collection_members and collections, and those policies would check each
  other's tables. That can cause infinite recursion errors in Postgres, which
  usually needs security definer helper functions to work around.
- Errors are less clear. A denied select just returns no rows, and a denied
  insert gives a generic Postgres error. Turning those into helpful 403/404
  responses takes extra work.
- Harder to debug and test. Logic is split between TypeScript and SQL.
  Integration tests need real signed-in users, and policies don't get
  type-checked.

Middle ground

- Use both: the admin client and service checks for application logic, plus a
  few basic RLS policies as a safety net. That costs extra work, since every
  rule is written twice.
- Leave RLS on with no policies (the current state) and use only the admin
  client. This blocks any access that doesn't go through the backend at all, a
  reasonable default for Option 1.

For this project

Points that bear on the choice:

- All database access goes through the Express backend.
- AGENTS.md already says data access uses supabaseAdmin.from(...).
- The pin code is written in the Option 1 style.
- The planned collection permissions (owner, collaborator or viewer,
  can_add_pins, public or private) are where Option 2's cross-table policy
  problems would show up.

Against that, Option 2 gives stronger security guarantees and is closer to how
Supabase is designed to be used. The decision is your team's. Once you've
picked, I can make the repositories consistent.

❯ what does middleware do here?

⏺ Middleware in Express

Middleware is a function that runs between a request arriving and a route
handler sending the response. It has the signature (req, res, next), and it
can do one of three things:

- change the request and call next() to pass it on (for example, attach
  req.user)
- end the request early by sending a response itself (for example, a 401)
- pass an error along with next(err)

Express runs middleware in the order you register it with app.use(...) or
router.use(...), like a pipeline. app.ts already uses some built-in
middleware:

- cors(...) adds CORS headers.
- express.json() parses JSON bodies into req.body.
- The app.use((_req, res) => ...404) near the end catches any request no route
  matched.

A request flows like this:

request → cors → express.json → [authenticate] → pin controller → response
│
next(error)
↓
[errorHandler] → error response

The two planned middleware files

authenticate.ts runs before the pin controllers, because pinRoute.ts calls
router.use(authenticate). Its job would be:

1. Read the access token from the request (where it comes from is a design
   decision; it's commonly an Authorization: Bearer <token> header).
2. Check the token with Supabase.
3. If it's valid, attach the user to req.user and call next(). If not, reply
   401 and stop.

This is what lets requireUser(req, res) in pinController.ts find a user. It
keeps the token-checking code out of every handler.

errorHandler.ts is a special kind of middleware with four parameters, (err,
req, res, next). Express only calls it when something calls next(err) or a
handler throws. It's registered last in app.ts.

- Every pin controller wraps its work in try { ... } catch (error) {
  next(error) }.
- Errors the service throws, like notFound("Pin not found"), therefore end up
  in the error handler.
- The handler would check whether the error is an AppError. If so, it sends
  that error's statusCode and message. Anything else gets a generic 500.

Today the only error handler is the generic one at the bottom of app.ts, which
turns every error into a 500. That's why item 4 on Sunny's list is to import
the new handler in app.ts in its place.

Why use middleware

Each of these concerns is written once and applied to many routes:

- Authentication: one router.use(authenticate) protects every pin route.
- Error handling: controllers just call next(error) and don't build error
  responses themselves.

The exact details are design choices for your team: where the token comes
from, the error response format, and what goes into req.user.

❯ so it's a way of moving logic away from the functions for the endpoints  
themself?

⏺ Yes, more or less. It moves logic that many endpoints share out of the
individual handlers and into one place that runs before or after them.

The handlers then only deal with their own job. createPin should only have to:

1. read the input
2. call pinsService.createPin
3. send back the result

It shouldn't also have to verify a token, figure out who the user is, or
decide how a 404 should be formatted. Without middleware, those steps get
copied into every handler, and a handler that skips one becomes a bug or a
security hole.

You can see this half-done in pinController.ts right now:

- requireUser is called at the top of createPin, updatePin and deletePin.
  That's the per-handler version of an auth check. Once authenticate runs on
  the router, every handler can assume req.user exists.
- Every handler ends with catch (error) { next(error) }. The handler doesn't
  decide what the error response looks like. It hands the error to the error
  handler.

Two caveats:

- Middleware is for logic that's actually shared. Logic for one endpoint, like
  "title is required" for creating a pin, stays in the handler or the
  service.
- It isn't the only way to move logic out of handlers. This codebase also uses
  layers: controller → service → repository. The difference is when the code
  runs. Services and repositories hold the business and database logic that
  handlers call. Middleware holds the request-pipeline logic that runs around
  the handlers: auth, parsing, CORS, error formatting.

⏺ The usual pattern has three parts: read a Bearer token, check it with
Supabase, and attach the user to the request. Your auth endpoints already fit
it: login and signup return an access_token, and logout already reads
Authorization: Bearer <token>.

This is an example of the common pattern, not something I've added to the
repo.

// middleware/authenticate.ts
import type { Request, Response, NextFunction } from "express";
import { supabaseAdmin } from "../lib/supabase.js";

export async function authenticate(req: Request, res: Response, next:
NextFunction) {
// 1. Pull the token out of "Authorization: Bearer <token>"
const header = req.headers.authorization;
const token = header?.startsWith("Bearer ") ? header.slice(7) : "";
if (!token) {
res.status(401).json({ error: "Missing bearer token" });
return;
}

    // 2. Ask Supabase who this token belongs to (also checks signature +

expiry)
const { data, error } = await supabaseAdmin.auth.getUser(token);
if (error || !data.user) {
res.status(401).json({ error: "Invalid or expired token" });
return;
}

    // 3. Attach the user and continue to the route handler
    req.user = data.user;
    next();

}

TypeScript also needs to know that req.user exists, which is one of the
current type errors. That's usually done with a declaration file:

// types/express.d.ts
import type { User } from "@supabase/supabase-js";

declare global {
namespace Express {
interface Request {
user?: User;
}
}
}

Routes then opt in with router.use(authenticate), which pinRoute.ts already
does, and handlers read req.user.id.

Common variations

- Checking the token locally: supabase.auth.getClaims(token) checks the JWT
  signature against the project's signing keys without a network call to
  Supabase on every request. It's faster, but a logged-out token still passes
  until it expires. getUser asks Supabase each time, so it catches revoked
  sessions.
- Attaching a user-scoped client (the RLS approach, Option 2 from earlier):
  the middleware also creates a client with the user's token, something like
  req.supabase = createClient(url, publishableKey, { global: { headers: {
  Authorization: \Bearer ${token}` } } })`. Repositories then use that client
  so RLS policies apply.
- Loading the profile: some apps also fetch the profiles row so handlers have
  username without another query.
- Errors through next: the middleware calls next(unauthorized()) so the shared
  error handler formats the 401, rather than sending JSON directly.

Decisions for your team before adding it

1. Whether to use getUser (checks with Supabase on each request) or getClaims
   (checks locally, faster).
2. What req.user holds: the full Supabase User, just { id }, or also the
   username.
3. The 401 response format: inline JSON as above, or AppError through the
   error handler.
4. Whether to also attach a client using the user's token. This depends on the
   admin client vs RLS decision.
5. Which routes need it. Should GET /pins/:id on a public collection work
   without logging in? Right now router.use(authenticate) protects every pin
   route.

❯ explain getUser vs getClaims. don't we need to check with the supabase to  
verify authentication?

⏺ You don't necessarily need to contact Supabase to check that a token is
genuine. You do need to if you want to know whether it's been revoked.

Why a token can be checked locally

A Supabase access token is a JWT: a small JSON payload (user id, expiry,
session id, role) plus a cryptographic signature from Supabase.

- If your project signs tokens with an asymmetric key (a private/public key
  pair), only Supabase has the private key that creates signatures. Anyone can
  download the public key and use it to check them.
- If the signature checks out against Supabase's public key, the token really
  came from Supabase and hasn't been changed. Nobody can forge one without the
  private key.

So "verify the signature and check exp hasn't passed" proves authenticity
without a network request. That's the point of JWTs.

The two functions

getClaims(token)

- Fetches your project's public keys once, from
  /auth/v1/.well-known/jwks.json, and caches them.
- Checks the signature and expiry locally, then returns the token's claims
  (sub is the user id).
- It's fast: no request to Supabase per API call after the keys are cached.
- One catch: if your project still uses the older shared-secret signing
  (HS256), it can't check locally and falls back to asking Supabase, the same
  as getUser. Check which kind you have in the Supabase dashboard under JWT
  signing keys.

getUser(token)

- Sends the token to Supabase Auth (/auth/v1/user) on every call.
- Supabase checks the token and the current state in its database: whether the
  user still exists, isn't banned, and whether the session is still active.
- It returns the full, up-to-date User object.
- It costs a network round trip on every authenticated request.

Where they differ: revocation

A valid signature only proves the token was genuine when it was issued. Things
can change after that. That matters here because of your logout endpoint,
which calls supabaseAdmin.auth.admin.signOut(token, "local"). That ends the
session on Supabase's side, but the access token itself stays validly signed
until it expires (default lifetime 1 hour).

┌──────────────────────────────────┬────────────────────┬────────────────┐
│ After the user logs out (or is │ getClaims │ getUser │
│ deleted or banned) │ │ │
├──────────────────────────────────┼────────────────────┼────────────────┤
│ Old access token is used │ Accepted until it │ Rejected right │
│ │ expires │ away │
└──────────────────────────────────┴────────────────────┴────────────────┘

So with getClaims, logging out stops the refresh token working, but a stolen
or old access token keeps working for up to an hour. With getUser, logout
takes effect immediately.

Summary

┌───────────────────────┬─────────────────────────────┬──────────────────┐
│ │ getClaims │ getUser │
├───────────────────────┼─────────────────────────────┼──────────────────┤
│ Proves the token is │ Yes │ Yes │
│ genuine │ │ │
├───────────────────────┼─────────────────────────────┼──────────────────┤
│ Catches logout, │ No (only once the token │ Yes │
│ deletion or bans │ expires) │ │
├───────────────────────┼─────────────────────────────┼──────────────────┤
│ Network call per │ No (with asymmetric keys) │ Yes │
│ request │ │ │
├───────────────────────┼─────────────────────────────┼──────────────────┤
│ What you get │ Claims in the token (id, │ Full current │
│ │ role, expiry, …) │ user record │
└───────────────────────┴─────────────────────────────┴──────────────────┘

Both are standard choices. getClaims is faster, and the risk is limited by
short token lifetimes, which suits many apps. getUser is stricter and means
your logout endpoint works the way users would expect. Which one to use is a
decision for your team.

⏺ "Attaching the user" just means setting a property on the req object. It works
because Express passes the same req object to every middleware and handler in
the chain.

The req object is shared

When a request arrives, Express creates one req object and one res object for
it. Every function in the pipeline gets those same two objects, not copies:

cors(req, res, next)
express.json(req, res, next)
authenticate(req, res, next)
updatePin(req, res, next)

So when one function changes req, every function after it sees the change.

You already depend on this. express.json() reads the raw request body, parses
it, and sets req.body. That's why createPin can read req.body.title. req.body
isn't built into HTTP; a middleware attached it.

authenticate does the same thing

// in authenticate
const { data } = await supabaseAdmin.auth.getUser(token);
req.user = data.user; // ← "attaching": just setting a property on the
shared object
next(); // ← hand the same req to the next function

// later, in updatePin — same req object
const userId = req.user.id; // ← reads what authenticate set

It's ordinary JavaScript. It's like passing an object through a series of
functions where each one can add a field:

const req = {};
authenticate(req); // sets req.user = { id: "abc", ... }
updatePin(req); // reads req.user.id → "abc"

Why this is useful

- The controller doesn't need to know where the user came from: tokens,
  headers, Supabase. It just reads req.user.
- The token check happens once per request, in one place, before any handler
  runs.
- If the user isn't logged in, authenticate sends a 401 and never calls
  next(). The handler doesn't run, so it never sees a request without
  req.user.

The TypeScript part

JavaScript lets you add any property to an object. TypeScript doesn't know
user belongs on Express's Request type, which is the current type error on
req.user in pinController.ts. The declare global { namespace Express {
interface Request { user?: ... } } } block from earlier tells TypeScript
"Requests may have a user property of this type." It doesn't change anything
at runtime; it only describes what the middleware does so the compiler accepts
it.

❯ restate the admin vs rls pros and cons

⏺ Here are the trade-offs again, updated for the code that now exists on both
branches.

Option 1: Admin client, permissions checked in the services

Pros

- Simple. One shared client and no SQL policies. Permission rules are ordinary
  TypeScript, easy to read, debug and change.
- It fits most of the existing code. The pin repository already uses
  supabaseAdmin, the pin service already checks "creator only", and Dia's
  service already checks "owner or collaborator" in code. Her repository would
  only need to switch clients.
- Complex rules are easy. Collection permissions involve owners, collaborators
  and viewers, can_add_pins, and public vs private. Those are a few ifs in
  code. As RLS policies they get complicated (see Option 2).
- Easy to test. Services can be unit tested with mocked repositories. You
  don't need real user tokens for each query.
- Clear errors. The service decides exactly when something is a 404, 403 or
  409, as both branches already do.

Cons

- Every check has to be remembered. A missed check exposes or allows changing
  any row, and nothing else catches it. Dia's endpoints currently trust
  user_id from the request body, which is exactly that kind of gap until
  authenticate is added.
- The secret key can do anything. A bug that bypasses a service check can read
  or change any row.
- Extra queries for permission checks. For example, loading a pin to compare
  creator_id before updating it.
- Only the backend can safely access the data. If the frontend ever queries
  Supabase directly, you'd need policies at that point anyway.

Option 2: User's token per request, plus RLS policies

Pros

- The database enforces permissions. A forgotten or buggy service check can't
  expose rows the policies deny.
- The standard Supabase approach. It's what the docs and tools assume, and the
  rules apply however the data is accessed (backend, frontend, other
  services).
- Rules defined once. One policy covers every query on that table, including
  ones written later.

Cons

- More setup. SQL policies for all five tables, managed through migrations and
  db:sync.
- Plumbing. The middleware has to build a client from each user's token
  (authenticate would attach it), and it has to be passed from controller to
  service to repository. Today both repositories import one shared client.
- Collection policies are tricky. Policies on collections, collection_members
  and collection_pins would all check each other's tables. That can cause
  infinite recursion errors in Postgres, which usually needs security definer
  helper functions to work around.
- Errors are less clear. A denied select returns no rows and a denied update
  affects 0 rows. Telling "not found" apart from "not allowed" takes extra
  work.
- Harder to test and debug. Logic is split between TypeScript and SQL,
  integration tests need real signed-in users, and policies aren't
  type-checked.
- Existing code changes more. Both repositories need a client per request, and
  the mocked unit tests would need rethinking.

Where things stand

- RLS is on with no policies for every table. Only supabaseAdmin can access
  anything right now.
- Pins use supabaseAdmin and work. Collections (both branches) use
  supabasePublic with no user token, so they won't work under either option as
  written.
- authenticate now uses getUser and puts the full User on req.user. Under
  Option 1 nothing else is needed. Under Option 2 it would also need to attach
  a client built from the user's token.
- Middle ground: keep RLS on with no policies and use the admin client
  everywhere. That's Option 1 with the database blocking all access from
  outside the backend. Adding a few basic policies later as a safety net is
  possible but means writing each rule twice.

This is still the team's decision. Whichever you pick, the collection
repository has to change.

❯ what's standard in crud applications

⏺ It depends on the architecture, and the two options come from different
traditions.

Apps with their own backend (Express, Django, Rails, Spring, etc.)

- The standard is application-level authorization. The backend connects to the
  database with one privileged account, and permission checks live in the
  code: services, middleware, or policy classes.
- That's how most CRUD apps have been built for a long time. Django's
  permissions, Rails' Pundit and CanCan, and checks in Express services all
  work this way.
- Database-level row security exists in Postgres but is fairly uncommon in
  this setup.
- Option 1 is the conventional setup for this.

Supabase-style apps (the frontend talks to the database directly)

- When there's no backend in between, the database is the only thing that can
  enforce permissions, so RLS is required. That's why Supabase's docs,
  examples and dashboard warnings center on RLS.
- Option 2 is the standard there.

Supabase plus your own backend (your setup)

- You'll see both. Many teams treat the backend as the only way in: secret key
  on the server, checks in services, and RLS turned on with no policies so
  nothing else can get in. That's the "middle ground" I mentioned earlier, and
  it matches how traditional backends work.
- Others pass the user's token through so RLS still applies as a second layer
  of protection. That's more common when some access also happens directly
  from the frontend, or when security requirements are stricter.
- Supabase's guidance is to keep the secret key on the server only. Using it
  there for trusted operations is a supported, expected pattern.

So for an app where everything goes through an Express backend, checking
permissions in the services is the more conventional approach in the wider
industry. RLS is what Supabase itself centers on, and what you'd need if the
frontend ever queries the database directly. "Standard" doesn't settle it
either way, so it's still your team's call.

❯ why is an error handler needed? like what are the downsides of just creating  
errors manually?

⏺ You need some error handler no matter what. The real question is how much
error-response logic goes there and how much is written inline in each
handler.

Why some handler is unavoidable

Not every error comes from a place where you can write a response:

- Unexpected errors: a database outage, a bug, a Supabase failure inside a
  repository. You can't add inline handling for errors you didn't predict.
  Something has to catch them, or the request fails with no proper response.
- Errors raised outside your handlers: express.json() rejecting malformed JSON
  happens before any of your code runs.
- Express has a built-in default handler. Without yours, it replies with an
  HTML error page (and the stack trace when not in production), not JSON.
  That's why app.ts already defines a custom one.

Writing every error response inline

auth.ts mostly works this way: res.status(409).json({ error: "Username is
already taken" }), right where the problem is found.

Pros

- Easy to follow. The status code and message sit right next to the condition
  that caused them.
- No extra pieces. No error classes or status tables.
- Fine for small, simple handlers, especially for checking input in the
  controller.

Cons

- Only controllers can do it, because only controllers have res. Services and
  repositories don't. That's why pinService throws notFound(...): it can't
  send a response. To answer inline, the controller would have to check every
  possible result of every service call.
- Inconsistent error formats. Each handler builds its own JSON, so the
  response shape drifts. It's already happening:
  - auth.ts sends inline { error } responses.
  - pinService throws AppErrors carrying a code.
  - Dia's controller has its own ERROR_STATUS table keyed on message strings.
  - The frontend would have to handle three styles.
- Repetition. The same 401, 403 and 404 responses get rewritten in every
  handler. A change like "include an error code" or "hide internal messages in
  production" means editing every one of them.
- Easy to get wrong. Forgetting return after res.status(...) sends two
  responses and crashes. Forgetting to handle a case makes it fall through to
  a misleading 500 or a hung request.
- Logging is scattered. Each handler has to remember to log, as authenticate
  does with console.error.
- Leaking details. Inline handlers can easily send raw database messages to
  the client. Dia's controller does this deliberately for now, to make
  debugging easier.

Throwing errors and handling them centrally

pinService already works this way: throw an AppError, and the handler turns it
into a response.

Pros

- Any layer can report an error (service, repository, middleware) without
  knowing about HTTP responses.
- One response format, defined once.
- One place for policy: logging, hiding internal details, mapping database
  errors (e.g. duplicate key → 409), and handling JSON parse errors.
- Shorter handlers: they deal with the success case and call next(error).

Cons

- The flow is less obvious. You have to know that a throw in the service
  becomes a 403 somewhere else.
- More setup: error classes, helpers like forbidden(), and the handler itself.
- Tempting to overuse. Simple checks are often clearer inline.

In practice

Most Express apps use both. Simple request checks (like "title is required")
are answered inline in the controller, and everything from deeper layers, plus
anything unexpected, goes to one error handler. Your codebase already does a
bit of each but doesn't map AppError to its status yet. Which mix to use, and
the error response format, are decisions for your team.

❯ what is standard error handler behavior for a crud app

⏺ Most Express CRUD apps' error handlers do roughly the same things:

1. Sit last and catch everything

- Registered after all routes, with the four-parameter signature (err, req,
  res, next).
- It's the single place every next(err) and every thrown error in an async
  handler ends up (Express 5 forwards those automatically).

2. Send known errors with their own status

- The app defines its own error type, like your AppError, with a status code,
  a short machine-readable code, and a message.
- The handler sends those as they are: 400 bad request, 401 not logged in, 403
  not allowed, 404 not found, 409 conflict.

3. Turn library and database errors into proper statuses. Common
   Postgres/Supabase cases:

┌──────────────────────────────────────────┬──────────────────────────────┐
│ Error │ Usual response │
├──────────────────────────────────────────┼──────────────────────────────┤
│ Unique constraint violated (23505) │ 409 Conflict │
├──────────────────────────────────────────┼──────────────────────────────┤
│ Foreign key violated (23503), e.g. a pin │ 400 or 409 │
│ pointing at a nonexistent user │ │
├──────────────────────────────────────────┼──────────────────────────────┤
│ Missing required field / check │ 400 │
│ constraint failed (23502 / 23514) │ │
├──────────────────────────────────────────┼──────────────────────────────┤
│ Value in the wrong format, e.g. a │ 400 │
│ malformed UUID (22P02) │ │
├──────────────────────────────────────────┼──────────────────────────────┤
│ .single() found no row (PGRST116) │ 404 │
├──────────────────────────────────────────┼──────────────────────────────┤
│ Unknown column in the request (PGRST204) │ 400 │
├──────────────────────────────────────────┼──────────────────────────────┤
│ Malformed JSON body / body too large │ 400 / 413 (from err.status) │
│ (express.json) │ │
├──────────────────────────────────────────┼──────────────────────────────┤
│ Failed validation │ 400 or 422, often listing │
│ │ which fields are wrong │
└──────────────────────────────────────────┴──────────────────────────────┘

4. Everything else becomes a generic 500

- Unknown errors get 500 with a vague message like "Internal server error".
- The real message, stack trace and SQL details are never sent to the client,
  because they can reveal internals. Some apps show more detail in development
  only.

5. Log based on severity

- 5xx: log the full error and stack, since it's a bug or an outage.
- 4xx: log briefly or not at all, since it's the client's fault and would
  flood the logs.
- Many apps add a request id, method and path to each log line so errors can
  be traced.

6. Use one consistent response shape. Common choices:

- { "error": "message" } (what auth.ts sends now)
- { "error": { "code": "not_found", "message": "Pin not found", "details": ...
  } }
- RFC 9457 "problem details" (application/problem+json) with type, title,
  status and detail

⏺ Oxlint doesn't format code. A linter only finds problems, and some of those it
can fix for you. Layout (spacing, quotes, line breaks) is a formatter's job.
So "automatically format" means one or both of these.

1. Auto-fix lint problems: built into Oxlint

oxlint --fix applies the safe fixes for problems it finds, such as removing
unused imports, and reports what's left. It also has:

- --fix-suggestions: fixes that might change behavior
- --fix-dangerously: riskier fixes

The usual minimal change is one script in backend/package.json:
"lint:fix": "oxlint --fix"

2. Formatting: needs a separate tool

- Prettier. It's already installed at the repo root (npm run prettier writes
  prettier --write .). It has no config or ignore file yet, and it runs over
  the whole repo. The usual setup: a .prettierignore (to skip dist/,
  database.types.ts, ai_logs/, the committed node_modules/) and either a
  backend format script or the root script.
- Oxfmt. The formatter from the same project as Oxlint (latest version
  0.75.0). It's designed to produce Prettier-compatible output and is much
  faster. It's still pre-1.0. Choosing it would mean a second formatter in the
  repo alongside the root Prettier, unless the frontend switches too.

Oxlint's default rules don't check layout, so a formatter and the linter don't
conflict. The usual order is to lint and fix first, then format.

3. Making it automatic

"Automatically" can mean different points, and teams often use more than one:

- Format on save in the editor. VS Code with the Prettier or Oxc extension,
  set up in .vscode/settings.json. No dependencies, but each person has to
  have the extension.
- A pre-commit hook. For example husky with lint-staged, running oxlint --fix
  and the formatter on files you're about to commit. Two more dev
  dependencies, and it applies to everyone.
- A CI check. oxlint plus prettier --check (or oxfmt --check) fails the build
  if code isn't formatted. It doesn't change code, it enforces.

Decisions for you

1. Which formatter: the existing Prettier, or Oxfmt.
2. Its settings: keep the defaults, or set things like quotes, semicolons,
   line width. The backend's auth code already looks like Prettier defaults.
3. When it runs: a script you run yourself, format on save, a pre-commit hook,
   a CI check, or a combination.
4. Which fixes to allow: only --fix (safe), or also suggestions.

Running a formatter for the first time will reformat most of the backend,
including pinRepository.ts and pinService.ts from Sunny and Dia's branch files
after the merge. It's best done in its own commit, and ideally after merging
Dia's branch so the formatting changes don't add to the merge conflicts.
